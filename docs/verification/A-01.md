# A-01 — demo authentication checkpoint

Status: IN_PROGRESS. Source and controlled-adapter tests exist; the required two-browser login has not run.

## Implemented

- `auth/otp.ts`: normalizes Pakistani numbers, generates a six-digit DEMO code, stores its HMAC digest, signs sessions, and resolves current users using both session ID and role. Public clients may select worker/customer only. No SMS is sent.
- `auth/redis-otp.ts`: five-minute TTL, atomic compare-and-consume Lua operation, five failed attempts per issued code, preserved TTL on a failed attempt, and rejection of unrecognized stored roles. A consumed code cannot be reused. The Lua script still requires real Redis execution testing.
- `db/identities.ts`: user upsert preserves an existing role; worker creation and user creation share a transaction. Failure rolls back; a failed rollback discards the client exactly once. Explicit private identity projections validate responses and normalize empty worker tag counts to zeros. Stored-data errors stay internal.
- HTTP: `/api/auth/otp/start`, `/api/auth/otp/verify`, `/api/me`. No-store responses, same-origin mutation checks, bounded JSON bodies, Redis limits, signed HttpOnly cookies and no token in response JSON. Limits fail closed on Redis errors. Keys hash caller IPs; OTP keys follow the plan's `otp:{phone}` form. Neither is logged.
- Web: W1 tap continuation, W2 and C1 phone/code forms in Urdu/Roman/English. Visible DEMO/no-SMS disclosure, auto-filled demo code, explicit confirm button, expired/invalid/role/rate/network feedback, cancellable requests with a timeout, and `/me` confirmation before showing sign-in success. No session token is stored in browser storage. Later onboarding screens remain placeholders.
